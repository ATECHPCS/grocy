# Phase 4 — UI Design Contract

> Visual and interaction contract for reusable conversion validation and explanation in the established Grocy interface. Generated by gsd-ui-researcher and approved by the six-dimension UI safety check.

## Scope and Authority

Phase 4 adds compact, explainable conversion status to Grocy's native quantity-unit conversion editor, the product-specific conversion area, and the resolved-conversions view. It also adds one maintainer-only, read-only **Conversion coverage** report. It does not replace Grocy's conversion forms, product form, Save controls, cache consumers, or normal persistence path.

The visual contract makes these boundaries visible:

- The existing quantity-unit conversion form and its normal Grocy Save flow remain the only way to persist a universal default or product-specific override. A successful pre-save validation is required, then the server repeats that validation inside the authoritative save/projection operation.
- A product-specific conversion is a **Product override**. It has higher precedence than a food-type profile, which has higher precedence than a universal conversion. The UI never implies that row order or shortest path chooses the result.
- Food-type mass/volume conversions are always labelled **Approximate** and display their named source and source version. They apply only when the product has an explicit current Phase 3 taxonomy leaf.
- Pack, can, bottle, piece, and other count/package relationships remain product- or barcode-bound. They never appear as universal or food-profile candidates.
- Existing product-specific rows are inspection-only in Phase 4. No cleanup, replacement, removal, bulk action, or confirmation dialog is introduced; that work belongs to Phase 6.
- Reusable rules remain inactive until the dual-branch characterization gate is passed. The UI may show native Grocy rows, but must not claim that a Phase 4 profile or projection is active before that gate is green on both maintained branches.

All new strings go through Grocy localization. Display named sources, closed reason/status labels, and version identifiers only; never expose provider payloads, raw SQL, cache-trigger text, stack traces, URLs, credentials, or household-data diagnostics.

## Visual Hierarchy and Interaction

### Native quantity-unit conversion editor

Use the existing `quantityunitconversionform` layout and retain its current order: from unit, to unit, factor, the existing human-readable forward/inverse sentence, user fields, then Save. Insert one compact **Reusable conversion validation** region after the inverse sentence and before user fields; it is a bordered secondary surface, not a nested decorative card.

For a universal default (`product_id` absent), the region shows, in order:

1. `Dimension: Mass` or `Dimension: Volume` as read-only text for each selected unit.
2. The candidate pair as `1 {from unit} = {full-precision factor} {to unit}`. The existing Grocy quantity-decimal setting formats the normal sentence; this candidate line exposes the stored precise factor without rounding it away.
3. `Source: NIST SP 811 · {source version}` for an approved universal factor. Source/version are module-owned read-only provenance, never browser-entered free text.
4. The current impact status and its next action.

When units are incomplete, say `Choose both quantity units and a positive factor to validate this conversion.` When a pair mixes dimensions, show a blocking `alert-danger`: `Mass and volume cannot be used in one universal conversion. Use an explicitly assigned food-type profile or a measured product conversion instead.` When either unit is not an allowed Phase 4 mass/volume unit, show a blocking alert: `This quantity-unit pair is not eligible for a reusable default. Keep package and count conversions on the product.`

For a product-specific form (`product_id` present), keep the same region but label its source category `Product override` and state `This conversion takes precedence over any food-type profile and universal default.` It may use a measured density or package/count relationship, but it must still pass the candidate graph validation before Save. Do not label a manually entered product override approximate unless its own recorded source makes that true.

`Validate conversion impact` is the phase-owned primary action. It performs a read-only validation of the values currently in the form; while running, disable only this button and the native Save conversion button, display `Validating conversion impact…`, and keep the rest of the page usable. Changing either unit or factor invalidates a prior result and returns the region to `Validate this conversion before saving.`

An eligible result uses `alert-success`, a check icon, and `No blocking paths, cycles, reciprocal conflicts, or tolerance failures were found.` The existing Save control is then enabled and is labelled `Save conversion` in its accessible name. On submission, revalidate server-side; if the candidate changed or validation now fails, preserve all entered form values, do not persist or project the row, restore focus to the blocker heading, and require a fresh validation. Never add a second save endpoint, hidden automatic save, or a Phase 4 activation toggle.

### Product conversion area

In the existing **Product specific QU conversions** section, place a concise `Reusable conversion status` line between the heading/actions and the existing table. It is informational and read-only:

- Explicit taxonomy leaf plus approved profile: `Approximate profile: {profile name} · {source name} {source version}` with an `Approximate` badge.
- Explicit taxonomy leaf but no profile: `No estimate is available for this food type.`
- No explicit taxonomy leaf: `No estimate is available until this product has an explicit food classification.`
- Characterization gate incomplete: `Reusable conversion profiles are inactive until both branch checks pass.`

Do not make the status line a taxonomy editor and do not derive eligibility from product group, provider evidence, or a suggested leaf. The existing `Add` route remains a normal product-conversion dialog. Add an **Effective source** column to its table: direct rows are `Product override`; any inherited value is not synthesized into this table. The existing `Show resolved conversions` action remains the route to derived results.

### Resolved-conversions view

Extend the existing resolved-conversions DataTable with two visible concepts:

- **Source**: `Product override`, `Universal — NIST SP 811`, or `Approximate profile — {profile name} · {source version}`.
- **Status**: `Exact`, `Approximate`, `Unavailable`, or `Blocked`.

`Approximate` has a visible text badge and a supplementary triangle-exclamation icon; it must not rely on yellow color alone. Universal and product override rows use `Exact` text rather than a success-only color. A missing profile produces an `Unavailable` entry or contextual empty message; it never displays a guessed factor. A conflict produces a `Blocked` entry with no usable factor.

Keep the existing factor and "This means" explanation concise and rounded according to Grocy settings. Each row has a text-labeled 44px `Show conversion details` control that expands one semantic detail region in place (DataTables child row or equivalent), rather than opening a second page. Its accessible name includes the from/to units. The detail region shows, in this order: full-precision factor, source name/version, source category, precedence result, explicit taxonomy leaf when a profile applied, and the validated path/reciprocal outcome. `Approximate` appears before the factor in this region.

Retain the existing quantity-unit filter. Add source and status filtering only if it can use the established DataTables controls; otherwise keep those values as sortable columns. On mobile, keep from unit, to unit, source/status, and `Show conversion details` visible. Move the rounded factor and prose explanation into the expanded detail region before allowing horizontal scrolling. The existing filter collapse remains the mobile pattern.

### Maintainer-only Conversion coverage report

Add a separate authenticated page available only with `MASTER_DATA_EDIT`. It is read-only and must never write, project, activate, modify, or remove rules. Use the normal page title, an `h2` heading `Conversion coverage`, existing Bootstrap filters, and DataTables only where the result set benefits from sorting/filtering.

The page begins with one ruleset summary surface:

- `Ruleset ready` only when validation has no blockers **and** the dual-branch characterization and protected-consumer comparison are passed.
- `Ruleset has {n} blockers` when any dimension mismatch, competing effective path, reciprocal inconsistency, cycle, invalid factor, or tolerance failure exists.
- `Reusable rules are inactive until characterization passed on both branches.` when the implementation gate remains incomplete.

The summary lists the ruleset version, validation time, characterization state for both branches, and aggregate counts for covered pairs, unavailable profiles, redundant product overrides, and blockers. It may use `alert-success`, `alert-warning`, or `alert-danger`, but each state also has the exact text heading and count.

Below it, use these read-only sections in this fixed order: **Blocking issues**, **Coverage and missing paths**, **Effective sources**, **Redundant product overrides**, then **Characterization and protected behavior**. Empty sections remain visible with neutral empty-state copy; do not hide a category simply because it currently has no entries. A blocker row compares the conflicting unit pair/source/factors and names the correction category, but never proposes a nearest factor. The final section reports the check state for stock, recipes, purchase, consumption, price, quantity display, transfer, and meal plans as a compact check matrix; it does not replay those actions from the browser.

`Refresh validation report` is a read-only secondary action. While it runs, disable only itself, announce `Refreshing conversion validation report…`, retain the last complete report, and replace it only with the newer complete response. An unavailable report shows a recoverable error and `Try again`; it must not erase the last successful report or display raw exception text.

## Interaction States

| State | Visual contract | Allowed action / exit |
|-------|-----------------|-----------------------|
| Incomplete candidate | Neutral validation region with the missing-input instruction | Complete units/factor; no Save conversion |
| Validating candidate | Spinner plus `Validating conversion impact…`; only validation and Save controls disabled | Current response, changed form input, or recoverable request failure |
| Eligible candidate | Success alert with exact no-blocker message, source/version, and precise factor | Save conversion; any edit invalidates eligibility |
| Blocked candidate | Danger alert naming the pair and blocker category; no factor chosen or inferred | Correct units/factor/source, then validate again; Save remains disabled |
| Validation request failure | Warning: `This conversion could not be validated. Correct any visible fields or try again. Nothing was changed.`; entered values remain visible | Try validation again; Save remains disabled |
| Stale validation | Warning: `This validation is out of date. Validate the current conversion before saving.` | Validate again; never reuse a result for changed input or ruleset version |
| Exact resolution | Source and `Exact` visible in table/status | Show conversion details |
| Approximate profile | Source/version and `Approximate` visible before factor | Show conversion details; use conversion knowingly |
| No profile / unclassified | Neutral `No estimate is available…` status, no factor and no inferred substitution | Assign a taxonomy leaf in its existing Phase 3 surface or add a measured product conversion normally |
| Conflict / invalid projection | `Blocked` row and report entry, no effective factor exposed to consumer-facing UI | Correct source rule using native form, validate again |
| Characterization gate incomplete | Warning summary; no profile/projection marked active | Run the required branch characterization outside this UI, then refresh report |
| Report refresh failure | Existing report stays visible; warning says `The validation report could not be refreshed. Try again.` | `Try again`; no browser write |

Use a per-form candidate revision and a per-report request sequence. A late validation/report callback may update the DOM only if it matches the current revision/request; it must never enable Save, replace a newer status, or restore old provenance. Normal product edits, product Save controls, and unrelated Grocy views remain available during every read-only validation/report request.

## Responsive and Accessibility Contract

- Support 320px viewport width without horizontal scrolling. All direct controls, including `Validate conversion impact`, `Save conversion`, `Show conversion details`, and `Refresh validation report`, have a 44px minimum target on touch layouts.
- Below 576px, validation actions stack full width; dimension/source/factor metadata stacks in source order. At 576px and above, related actions may sit in the existing wrapping action row.
- The resolved table's essential source/status and details controls stay reachable at 320px; secondary factor/prose moves into the expanded details region as specified above.
- Use native `button`, `select`, numeric-input, table, heading, alert, and disclosure semantics. Do not make a badge, factor, or icon the sole interactive control.
- Use `role="status"` and `aria-live="polite"` for validation/report progress and eligible results. Use `role="alert"` for blockers and validation failures. After a block, focus the blocker heading; after a successful in-place report refresh, focus remains on the refresh button and announce the summary count.
- Every disclosure begins collapsed, has a visible text label, and preserves keyboard access. Do not put critical source/version or blocker information only in a hover tooltip.
- A visible 2px `var(--primary)` focus outline with 2px offset is required for any new phase-owned control. Preserve existing `.night-mode` contrast; any new light background/border selector gets a `.night-mode` equivalent. Respect `prefers-reduced-motion` and do not use essential motion.
- Color is never the only signal for an approximation, conflict, readiness, selected filter, or unavailable estimate. Pair each with explicit text and, when useful, a supplementary icon.

## Spacing Scale

Use only this established 8-point scale for Phase 4 additions:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label and inline provenance gaps |
| sm | 8px | Related metadata lines, badges, compact controls |
| md | 16px | Validation-region padding, form/status separation, report row padding |
| lg | 24px | Separation between report sections and major conversion subsections |
| xl | 32px | Major report/action separation on narrow layouts |
| 2xl | 48px | Existing page-region separation only |
| 3xl | 64px | Page-level spacing only; never inside compact conversion UI |

Exceptions: Bootstrap's existing 1px borders and the deployed 4px grocy_AI card rule remain intact. The 44px touch-target requirement is an accessibility dimension, not a spacing token. Do not introduce one-off Phase 4 gaps such as 6px, 10px, 12px, or 20px.

## Typography

Use exactly the established four sizes and two weights for all new/changed Phase 4 UI. Inherit Roboto and use sentence case.

| Role | Size | Weight | Line Height | Usage |
|------|------|--------|-------------|-------|
| Supporting | 14px | 400 | 1.5 | Source/version, dimensions, provenance, table metadata |
| Body / control | 16px | 400 | 1.5 | Factors, alerts, actions, row values, recovery instructions |
| Section / status heading | 20px | 500 | 1.2 | Validation, report section, blocker, and status headings |
| Page / card title | 24px | 500 | 1.2 | Conversion coverage page title and existing grocy_AI card title where reused |

Allowed weights are 400 and 500 only. Keep blocking/recovery text at 16px, not muted metadata. Use tabular numerals where available for factors, counts, and versions; allow long source names/versions to wrap with `overflow-wrap: anywhere` rather than ellipsizing decision-critical content.

## Color

Use Bootstrap/Grocy semantic classes so current night mode remains authoritative. The light-theme values declare the required hierarchy.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` | Native form and page surfaces, table cells, expanded details |
| Secondary (30%) | `#F8F9FA` with `#DEE2E6` border | Validation/provenance grouping, neutral coverage sections, unavailable state |
| Accent (10%) | Bootstrap `var(--primary)` / `#007BFF` | Validation action, active filter, keyboard focus, grocy_AI card rule, source-detail control |
| Destructive / error | `#DC3545` | Blocking validation and report error states only; Phase 4 has no destructive action |

Accent is reserved for `Validate conversion impact`, `Refresh validation report`, the active resolved-filter state, focus outlines, `Show conversion details`, and the existing grocy_AI identity rule. It must not color all factor text, source labels, table headers, badges, or routine secondary actions.

Semantic states use existing Bootstrap classes: success/check icon plus `Eligible` or `Ruleset ready`; warning/triangle plus `Approximate`, inactive gate, or stale validation; danger/error icon plus `Blocked`; and neutral text/border plus `Unavailable`. Never communicate any of these solely through color.
