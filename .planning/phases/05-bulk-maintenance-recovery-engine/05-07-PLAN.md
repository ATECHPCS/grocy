## Phase Goal

**As a** household maintainer, **I want to** apply my approved plan exactly once through a single safe transaction, **so that** the reviewed changes land atomically and neither a retry nor an interrupted run can duplicate or corrupt them.

<objective>
Deliver `ApplyPlan`: the approved apply set (selected, non-conflicted, checksum-bound) is written in one short `BEGIN IMMEDIATE` transaction with no network while the lock is held, each item routed through its registered typed operation, idempotent via a plan-checksum-keyed per-item completion ledger, and fully rolled back on any throw. Expose it as the authenticated, audited apply API action.

Purpose: generalize `ActivateVerifiedRuleset`'s single guarded, fail-closed, idempotent transaction into the reusable bulk apply, without becoming a parallel write authority.
Output: `ApplyPlan`, its apply endpoint + route, and its single-transaction / idempotency / rollback / resume tests. The audit ledger writes are added in 05-08.
</objective>

From `GrocyAiConversionService::ActivateVerifiedRuleset` (the idempotency/rollback template): idempotency is an existence check (`SELECT id ... WHERE evidence_hash = ?`) that skips the mutation when the row already exists; failure returns a bounded blocker after rollback. Reuse that existence-gate and fail-closed shape. LOCKED TRANSACTION SCHEME — one consistent scheme, not PDO's `beginTransaction()`/`commit()`: `ApplyPlan` takes the write lock up front with `$this->Db->exec('BEGIN IMMEDIATE')`, commits with `$this->Db->exec('COMMIT')`, and rolls back with `$this->Db->exec('ROLLBACK')`. Do NOT use PDO `beginTransaction()` (it opens only a DEFERRED transaction and does not take the write lock up front) and do NOT rely on `$this->Db->inTransaction()` to detect the outer transaction — after a raw `exec('BEGIN IMMEDIATE')` PDO's `inTransaction()` returns `false`, so the guard idiom used by `ActivateVerifiedRuleset` would misfire here.
From Plan 05-04 (operation registry): `ApplyPlan` dispatches each item by its registered operation name only; `assign_taxonomy_leaf` / `set_unclassified` delegate to `GrocyAiTaxonomyService::AssignProductTaxonomy`. An unknown operation fails closed with one bounded blocker before any write.
From Plan 05-06 (`DetectApplyConflicts`): the apply set is recomputed against live reality at apply entry; a drifted item is recorded `conflict` and never written.
From Plan 05-03 (`GeneratePlan` checksum): the stored plan `checksum` is a SHA-256 over the immutable content via the `CanonicalJson` idiom; the same recomputation binds the reviewed plan to the applied plan.
From `GrocyAiTaxonomyService::AssignProductTaxonomy(int $productId, array $assignment, bool $joinExistingTransaction = false)` (the 05-04 nesting-aware delegate): when `ApplyPlan` calls it inside the already-open `BEGIN IMMEDIATE` it MUST pass `$joinExistingTransaction = true` so the delegate skips its own `beginTransaction()`/`commit()`/`rollBack()` and joins the single outer transaction. The outer transaction ownership is signalled by that explicit flag — NOT by `inTransaction()`, which reads `false` after the raw `exec('BEGIN IMMEDIATE')`. The delegate never commits mid-apply.
From `GrocyAiApiController` (taxonomy endpoints): the `User::CheckPermission(...MASTER_DATA_EDIT)` + `ApiResponse`/`GenericErrorResponse` shape for the apply endpoint.

<threat_model>
## Trust Boundaries
| Boundary | Description |
|---|---|
| reviewed plan → applied plan | The applied artifact must be provably the reviewed one (checksum) and still valid against reality (conflict re-check). |
| apply request → durable write | The browser may confirm an apply but may never supply the operations, targets, or SQL that run. |
| retry / interruption → duplication | A re-run or crashed apply must never double-write a completed mutation. |
