## Objective
Close the conversion-cleanup requirements by verification, using the correct real-data invariant. Product-specific conversions are NOT inherently junk — on this inventory they are deliberate package-size definitions. Ship a read-only audit that (a) records the legitimate baseline and (b) trips only on rows that fail explicit integrity rules, so a future misconfiguration or genuine junk row is caught without flagging real package data.

## Facts (verified 2026-09-12 against the 06-01 snapshot)
`quantity_unit_conversions` = 80 rows = 62 global (`product_id IS NULL`) + 18 product-specific across 9 products (#186,499,500,501,502,503,505,506,507). Each of the 9 has a forward row (the product's stock/purchase unit — Piece or Can — → a measured unit g/oz/ml) plus its auto-generated inverse (the `quantity_unit_conversions_INS` trigger derives the inverse, so N authored rows → 2N stored). Verified: all 18 reference an existing product; all 18 have from OR to = the product's `qu_id_stock`/`qu_id_purchase`; all 18 have factor > 0; 0 exactly duplicate a global (from,to,factor). The globals are generic unit defaults (Can→Piece, Bag→Piece, Cup→Milliliter, …).

## Legitimate vs suspicious (the invariant)
A product-specific row is **EXPECTED** iff ALL hold:
1. `product_id` references an existing `products` row (referential integrity).
2. `from_qu_id` OR `to_qu_id` equals the product's `qu_id_stock` or `qu_id_purchase` (it defines the product's own discrete unit in measured terms — a package definition).
3. `factor` is finite and > 0.
4. It is not an exact `(from_qu_id, to_qu_id, factor)` duplicate of a global row (that would be redundant and belongs at global scope).

Any product-specific row failing any rule is **SUSPICIOUS** → the audit names it and exits non-zero. All 18 current rows are EXPECTED.
